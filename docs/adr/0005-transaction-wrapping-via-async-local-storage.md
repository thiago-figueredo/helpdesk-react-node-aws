# Every handler runs inside a transaction via a `withTransaction` decorator, propagated through AsyncLocalStorage

ADR 0004 originally specified that only actions needing cross-entity atomicity (`signup`, ticket transitions) would open `prisma.$transaction`, with the Service threading the resulting `tx` client through to Repositories as an explicit optional param. In practice this meant two different Repository call shapes depending on which Lambda was calling — some passing `tx`, most not — and left open the question of what a shared transaction helper would even wrap.

**Decision:** every Lambda handler, uniformly, is wrapped by a shared `withTransaction(fn)` decorator that opens a Prisma interactive transaction around the entire handler body — request parsing, Repository calls, and any external I/O (EventBridge `PutEvents`, SES `SendEmail`) alike — and stores the active `tx` client in an `AsyncLocalStorage` context for the duration of that call. Repositories no longer accept an explicit `client` param; they call a `getDbClient()` helper that reads the current transaction from the ALS context, falling back to the plain module-level `prisma` client if none is active. `withTransaction` also owns `DomainError` → HTTP response mapping (`toErrorResponse`): the handler body is left to throw, so a thrown `DomainError` rolls back the transaction before `withTransaction`'s own catch block converts it to a response — converting the error *before* it escapes `$transaction` would let Prisma see a normal return and commit a partial write.

This supersedes ADR 0004's "Service opens `prisma.$transaction`, threads `tx` through as an explicit param" paragraph — Services and Repositories no longer manage transactions or take a `tx`/`client` argument at all.

**Why:** chosen for the same "no Lambda is ever the exception" consistency argument already made in ADR 0004 for the Service/Repository/Mapper layering itself, rather than re-deriving per-Lambda whether atomicity is needed. Explicit `tx`-param threading was rejected because it forces every handler and Service signature to carry a param most of them only forward, never use directly.

**Consequences:** Neon has no connection pooler in front of it (ADR 0002), so every request — including pure reads — now holds a DB connection open for the full handler duration, including CPU-bound work (bcrypt hashing in `signup`) and external network calls (EventBridge, SES) that live inline in a handler. A slow or failed external call now rolls back an otherwise-successful DB write, rather than the write committing and the external call happening after — a deliberate uniform trade-off, not special-cased per Lambda. `getDbClient()`'s silent fallback to the plain `prisma` client (rather than throwing) when no ALS context is active means a future Lambda that's accidentally not wrapped in `withTransaction` degrades to an untransacted write instead of failing loudly — worth revisiting if that ever masks a real bug.
