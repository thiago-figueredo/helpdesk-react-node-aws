# Every Lambda uses a Service + Repository + Mapper, not direct Prisma calls

`signup-handler.ts` currently calls `prisma` directly: it builds the nested `user.create`/`tenant.create` write, catches `Prisma.PrismaClientKnownRequestError` by error code, and hand-assembles the response object, all inline in the handler. That's fine for one Lambda, but the same shape — persistence, ORM-error translation, and DTO assembly all inline — would otherwise get re-derived 17 times, including inside the ticket-transition Lambdas that already need a `SELECT ... FOR UPDATE` transaction (see "Atomic update mechanism" in `docs/backend/design.md`).

**Decision:** every Lambda, uniformly, gets a Service plus entity-scoped Repositories plus Mappers — no handler talks to Prisma directly, regardless of how simple its persistence need looks.

- **Repository**: one per entity (`UserRepository`, `TenantRepository`, `TicketRepository`, `MessageRepository`, `NotificationRepository`), shared across every Lambda that touches that entity, built on top of the tenant-scoped Prisma Client Extension from ADR 0001. Repositories catch Prisma-specific failures (e.g. unique-constraint violations, error code `P2002`) and throw domain errors — nothing above the Repository ever sees a Prisma type or error shape.
- **Mapper**: two explicit, separately-testable functions per entity — `toDomain()` (Prisma row → Domain object, called inside the Repository, strips persistence-only fields like `passwordHash`) and `toResponseDto()` (Domain object → the Zod response shape from `@yourname/helpdesk-shared`, called at the Service/handler boundary).
- **Service**: one per Lambda (e.g. `SignupService`), orchestrates Repository calls. ~~Where an action must be atomic across entities..., the Service opens `prisma.$transaction` and threads the transaction client through as an optional `tx` param on each Repository method.~~ **Superseded by [ADR 0005](./0005-transaction-wrapping-via-async-local-storage.md):** transaction management moved out of the Service entirely — every handler is wrapped in a shared `withTransaction` decorator, and Repositories read the active client via `getDbClient()` (AsyncLocalStorage) instead of an explicit `tx` param.
- **Errors**: domain errors are self-describing — a `DomainError` base class carries its own HTTP status in the constructor (e.g. `class DuplicateEmailError extends DomainError { constructor() { super(409, "Email already in use"); } }`). A shared `api/src/lib/error-response.ts` utility does `instanceof DomainError` and builds the HTTP response, used by every handler from the start.
- **Layout**: new flat, hyphenated, top-level folders parallel to `api/src/lambdas/` — `api/src/repositories/`, `api/src/services/`, `api/src/mappers/`, `api/src/domain/` — matching the naming style `CLAUDE.md` already fixes for Lambda handlers.

**Consequences:** this is more ceremony than 17 small Lambdas strictly need on a one-week build, and it's a deliberate deviation from the "one Lambda per business action, literal SRP example" simplicity argument already in `PRD.md` — chosen anyway for consistency (no Lambda is ever "the exception that talks to Prisma directly") and because demonstrating the pattern cleanly is part of the point of this portfolio build. Rollout is incremental and test-driven: layering is only built for a Lambda once that Lambda has a failing test driving it (starting with `signup`), not pre-built ahead of the other 16. This refactor does not add new test files — `signup-handler.test.ts` stays the sole, already-green integration test the layered implementation is built under.
